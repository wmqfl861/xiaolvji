## Executed native source diagnostic

`scripts/probe_zcode_source.py` executes a small dependency-free closure from the
actual pinned ZCode source. It checks the exact HEAD, then compares every file
to its Git blob before executing any source. Missing files, modified bytes,
symlinks, other commits, and unavailable local Git objects fail. Git lazy fetch
and ambient Git configuration are disabled in the diagnostic; it never fetches
source or installs packages automatically.

The diagnostic transforms the verified TypeScript files with Node's built-in
`stripTypeScriptTypes`, then runs ZCode's actual option-map compiler, evaluator,
merge-patch logic, agent-tool alias predicate, runtime environment sanitizer,
disallowed-tool argument extractor, and global argument parser.
No Zod replacement, provider replacement, or agent-loop stand-in is involved.
The only configuration inputs are generated by Xiaolvji's production renderer
using synthetic model names and a synthetic capability. Argument inputs come
from the production `build_command()` adapter with synthetic prompts.

The executed cases cover:

- Responses and Chat Completions with exact `high` and `ultra` effort strings
  and output budgets, including the renderer's maximum integer bound.
- Anthropic enabled thinking with an explicit budget, disabled thinking, and
  adaptive thinking with an explicit output-effort field.
- JavaScript model-regex matching with punctuation, prefix/suffix rejection,
  and rejection of names that would match an accidentally unescaped regex.
- Unchanged explicit model capability booleans and selected quality values.
- Preservation of the three explicit provider configuration environment keys
  and removal of synthetic ambient HTTP/HTTPS proxy settings by the inspected
  native sanitizer.
- Recognition of both native delegation aliases, `Agent` and `Task`, and
  their inclusion in Xiaolvji's disallowed-tool list.
- Native rejection of malformed expressions, unknown expression variables, and
  a missing effective reasoning value.
- Exact prompt and workspace preservation through both native argument-parsing
  stages, including Unicode, newlines, quotes, spaces, and option-like prompts.
- ASCII and multibyte prompts at the adapter's 120,000-byte limit on this Linux
  run. On Windows, those cases also respect its lower command-line bound.
- Unchanged guarded mode, disabled workflows, stream-json output, all seven
  denied native delegation/workflow tools, and no positional protocol command.
- Native rejection of the former split `--prompt`, value encoding for three
  option-like prompts, as negative controls for the fixed argument boundary.

The run passed seven mapping cases, three expression/quality negative controls,
three alias controls, fourteen proxy-removal controls, seven argument cases,
and three argument negative controls. Eleven source files are
recorded individually with SHA-256 hashes in the report. Six Python tests passed,
including the opt-in integration and provenance rejection scenarios.

The report retains its source-only `evidence_level: native_mapping_only`
classification and adds `argument_parser_tested: true`. It keeps
`configuration_schema_loaded`, `cli_launched`, `real_model_request_tested`, and
`native_execution_ready` false. Executing these pure native functions does not
prove full configuration loading, SDK request construction, HTTP streaming,
hook trust, tool exposure, or sandbox compatibility. It cannot be used as an
admission certificate.

### Reproduce the diagnostic

Use an already complete, clean checkout of the pinned source. The example
`/path/to/ZCode` must be replaced by that actual checkout path. Node.js 24.14 or
later in the 24.x series is required for this diagnostic; the full upstream
build still uses its own pinned toolchain.

```sh
python3 scripts/probe_zcode_source.py \
  --source /path/to/ZCode \
  --node /absolute/path/to/node \
  --report validation/zcode-source.json

XIAOLVJI_ZCODE_SOURCE=/path/to/ZCode \
XIAOLVJI_ZCODE_NODE=/absolute/path/to/node \
PYTHONPATH=src PYTHONDONTWRITEBYTECODE=1 \
  python3 -m unittest tests.test_zcode_source -v
```

Without `XIAOLVJI_ZCODE_SOURCE`, the actual-source integration test is explicitly
skipped with a reason. The small Git provenance tests still run. Never interpret
a skipped source integration test as passed native evidence.

### Lossless prompt arguments

The pinned CLI first extracts `--disallowed-tools` arguments, then calls
Node's strict option parser. A separate `--prompt`, `--help` pair is therefore
invalid even when `--help` was intended as literal task text. A prompt equal to
`--disallowed-tools=Read` is also inspected by the earlier extractor.

Xiaolvji now encodes the prompt in one `--prompt=<exact text>` argv entry.
The native parser preserves the complete text while the fixed guarded mode,
workflow setting, and denied-tool list retain their intended values. This uses
no shell, adds no escaping to the prompt itself, and preserves the existing
size limits; an oversized prompt is rejected instead of truncated. The probe
executes these actual native parser functions but does not launch the CLI or
establish that its tools enforce the parsed settings at runtime.

## Configuration and immutable-file behavior

The complete source confirms the provider rule and model-property shapes used
by [HOST-CONFIG-CONTRACT.en.md](HOST-CONFIG-CONTRACT.en.md). The native
option-map execution now verifies the generated expressions against ZCode's
actual evaluator. Full Zod schema loading still requires its real dependency.

The CLI's provider environment preparation returns the supplied explicit
builtin/personal configuration paths when both are present. Its provider
registry enables builtin remote refresh only when a bundled-source environment
path is supplied. Xiaolvji does not supply that additional path. The CLI also
loads a workspace `.env` using `override: false`; this is a reason to test the
complete launch, not a reason to assume all other runtime settings are pinned.

Xiaolvji's sealed provider files and protected ancestor mounts are intentionally
immutable during an attempt. The native personal configuration repository uses
atomic replacement for updates. A CLI path that tries migration, persistence of
a different model selection, or replacement of those mounted files must fail.
Do not make the parent directories writable to make such a path succeed. A
future native acceptance probe must demonstrate that ordinary execution can
read the exact configuration without rewriting it, and report any incompatible
native write as a specific blocker.

## Native result semantics

The pinned `--output-format stream-json` implementation writes a final
`type: "result"` line containing `sessionId`, an optional `turnId`, response
text, and a projection status, then returns process exit code 0. It does not
check the projection status before returning. A zero exit code alone therefore
cannot prove a successful native task.

Normal `TurnComplete` projection reduction sets the session to `idle`, while
`TurnError` sets `error`. However, `TurnCompletePayload.resultType` also includes
`cancelled`, `error_max_turns`, `error_max_budget`, `error_during_execution`, and
`error_max_tool_calls`. A complete event sequence must consequently preserve the
root session and turn identity, require an explicit successful result type, and
reject failed/cancelled/ambiguous results even when the process exits 0 and the
projection is idle. Slash-command exits without a model turn cannot satisfy an
implementation task's native-turn evidence.

Native events remain reports from the worker. They never release a managed slot
or replace the controller's process-tree exit proof, immutable candidate,
quality checks, or reviewer acceptance.

The standalone event adapter now uses the same bounded strict JSON loader as
native-result validation. It rejects numeric exponent overflow such as `1e400`,
excessive nesting, duplicate keys, and escaped unpaired Unicode surrogates in
nested payloads. Public `INVALID_EVENT` diagnostics omit untrusted JSON values
and duplicate-key text. The complete-result validator already applied this
strict loader; this change closes the inconsistency in standalone event parsing.

## Coordinator MCP tool names

The pinned [plugin MCP loader](https://github.com/zai-org/ZCode/blob/a60ba6a7e5a06742270ca605f5d2cc2766afa7e1/apps/zcode-cli/packages/adapters/src/plugins/mcp.ts)
prefixes a plugin server key with `plugin:<manifest-name>:`. Its
[tool descriptor](https://github.com/zai-org/ZCode/blob/a60ba6a7e5a06742270ca605f5d2cc2766afa7e1/apps/zcode-cli/packages/adapters/src/mcp/descriptor.ts)
replaces punctuation other than hyphens/underscores with underscores and uses
`mcp__<server>__<tool>`. For this package's manifest and server key, both named
`parallel-development`, the resulting exact prefix is
`mcp__plugin_parallel-development_parallel-development__`. A separately wired
direct server named `parallel-development` uses `mcp__parallel-development__`;
an explicitly configured direct server named `parallel_development` uses
`mcp__parallel_development__`.

The coordinator Hook recognizes only those exact reserved namespaces and the
controller's five declared MCP tool names. It returns an empty decision to defer
to native permissions; it does not issue a grant or infer worker identity.
The server independently authenticates its principal, exposes six read tools
to readers, and requires planner authority for task registration. Native Agent,
Workflow, arbitrary shell, foreign namespaces, bare tool names, and additional
suffixes do not obtain that exception. These naming rules are source evidence;
installed plugin loading and actual Hook delivery still require ZCode acceptance.

## Complete CLI build and remaining acceptance

In a deployment environment that can install the upstream's actual locked
dependencies, follow its
[quick start](https://github.com/zai-org/ZCode/blob/a60ba6a7e5a06742270ca605f5d2cc2766afa7e1/apps/zcode-cli/docs/usage/01-quickstart.md):

```sh
git clone https://github.com/zai-org/ZCode.git
cd ZCode
git checkout --detach a60ba6a7e5a06742270ca605f5d2cc2766afa7e1

# Verify these are the documented Node 24.14.0 and pnpm 10.33.2 first.
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm --filter @zcode/cli... build
node apps/zcode-cli/packages/cli/dist/zcode.cjs --version
```

The CLI output is a Node bundle with adjacent runtime resources, not a standalone
script whose dependencies may be discarded. The source build and any optional
SEA packaging must keep their actual toolchain and assets. A readiness identity
for a Node distribution must cover its executable closure, not merely the
launcher script or version string.

Before enabling strict native jobs, still establish actual immutable
configuration loading, model/quality wire values, native delegation-tool
suppression, applicable managed requirements and Hook trust, MCP loading where
required, successful tool execution inside the declared filesystem scope,
denied out-of-scope access, complete streamed success/failure semantics,
cancellation, and process-tree recovery. These checks require a real installed
CLI. This source-only diagnostic does not waive them.
