# 0.5.0 调度公平性、队列诊断与运行指标

这一版让协调器能回答三个具体问题：下一个任务为什么排在这里，它为什么尚未派发，以及实际运行留下了哪些可统计的证据。调度顺序由程序实现；Skill 指导合理拆分和持续发现机会；Hook 继续只处理实际覆盖到的宿主操作。质量门槛、独立审核和槽位回收的权限没有改变。

## 1. 防止旧任务长期被插队

旧实现优先所有 verifier，再比较固定优先级，只有同优先级任务才按登记顺序排序。这不是防饥饿机制：不断到来的验证任务或高优先级任务可能让旧的独立任务一直等下去。

现在，所有任务使用相同的有界排序公式：

```text
base_rank = priority + role_bonus
effective_rank = min(120, base_rank + floor(registration_age_seconds / 30))
```

| 参数 | 当前实现 |
| --- | --- |
| `priority` | 任务已批准定义中的 0–100，默认 50 |
| verifier 加分 | 20 |
| integrator 加分 | 10 |
| 其他角色加分 | 0 |
| 老化速度 | 从登记开始，每满 30 秒加 1 分 |
| 共同上限 | 120 |
| 同分顺序 | 更早的登记事件优先，再按项目和任务 ID 确定顺序 |

优先级为 0 的 worker 在累计登记年龄达到 3,600 秒后到达共同上限，此后比它晚登记的 verifier 即使优先级为 100，也不能靠更高分数一直插队。默认优先级 50 的 worker 在 2,100 秒达到上限。

**这不是一小时内一定启动的承诺。** 依赖未满足、文件范围冲突、资源被占用、项目暂停、重试退避或未知进程仍占槽时，任务仍不得启动。质量工作获得有限加分，所有质量门槛继续强制执行。

登记时间来自持久事件，重启不会清零。`waiting_age_seconds` 的含义是登记年龄，包含依赖等待、退避和旧尝试执行时间，不是连续 READY 时长。计算出的登记年龄为负时按零处理；一般时钟回退只会减少计算年龄。系统时钟仍会影响老化速度。

## 2. 查看真实准入阻塞

```bash
parallel-dev --state-dir /absolute/controller-state queue --project my-project --limit 100
```

MCP 对应 `parallel_queue`。该接口使用一个数据库读快照和一次时钟采样，最多返回 200 个摘要。所有已登记任务都属于查询范围：eligible 的任务排在前面，活动或终结任务仍可出现在后面的摘要中。`total` 是选定项目范围的任务数，`truncated` 说明结果是否截断；它不是可执行任务的总数。

| 字段 | 应怎样解释 |
| --- | --- |
| `eligible` | 当前项目、任务状态、退避和依赖允许参与准入；尚未证明容量或资源可用 |
| `dispatchable` | 该任务单独面对当前快照时，通过完整准入检查 |
| `priority` / `base_rank` / `effective_rank` | 已登记优先级、角色加分后的分数、老化后的分数 |
| `blockers` | 当前已发现的阻塞类型，包括全局/项目容量、写入范围、独占资源、退避、依赖等 |
| 冲突的 `owner` | 占用方的 attempt/project/task ID；不返回资源名、路径或原始任务文本 |
| `blocker_count` / `blockers_truncated` | 每项最多展示 16 个合并后的阻塞摘要，完整计数另列 |
| `capacity` | 全资源域容量，包含其他项目和不确定实例 |
| `project_capacity` | 当前任务所在项目的容量，同时受全局剩余容量约束 |
| `event_cursor` | 此数据库快照对应的全域事件位置 |
| `advisory` | 固定为 true；该查询从不预留槽位 |

如果只剩一个槽位，两个任务都可能显示 `dispatchable=true`，因为它们是分别评估的。它们也可能彼此存在尚未形成活动租约的冲突。只有后续 `reserve()` 在原子事务里重新检查并分配容量，才有权启动一个任务。文件系统检查是当时的观察，同样不能代替再次准入。

准入和诊断共用检查函数，避免出现两个不同版本的容量、依赖或冲突规则。原有 `reserve()` 仍按首次失败立即拒绝，只有诊断请求收集额外阻塞原因。对于当前不 eligible 的任务，先返回首个状态/依赖阻塞，不推测全部下游原因。

### 查询预算和错误

查询在读取和排序之前检查总体预算。选定范围最多 10,000 个任务、10,000 个项目；全域最多 20,000 个活动尝试、20,000 个租约。超过预算返回 `QUEUE_LIMIT`，不把部分任务冒充完整排序。减小 `--limit` 只缩小输出；按项目过滤才能减少任务/项目总体，跨项目租约仍必须纳入判断。

缺失、错配或时间无效的登记事件返回 `QUEUE_INCONSISTENT`，调度器也不会静默跳过该任务。应诊断并恢复可信状态，不应直接改账本来清除阻塞。

## 3. 查看运行指标

```bash
parallel-dev --state-dir /absolute/controller-state metrics --project my-project
```

MCP 对应 `parallel_metrics`。它只读取当前账本的完整保留历史，不读取 Worker 日志、工作文件或提供商凭据，不创建任务、不修改状态，也不记录验收。

### 已有指标

| 指标 | 准确含义 |
| --- | --- |
| 登记到首次预留 | 每个首次获得槽位的任务，从登记事件到第一笔预留的时长；包括依赖和退避等待 |
| 预留到释放 | 一次尝试占用控制器容量的时长，包括启动准备和退出确认 |
| 首次启动确认到终态观察 | 有实际启动确认的尝试，从首次确认到可靠终态事件；重复确认不重复计时 |
| 释放到范围内下一次预留 | 每个已释放尝试，到选定范围内后续第一笔预留的事件间隔；可能包含空闲期 |
| 活动预留年龄 | 当前尚未释放的尝试已占用多久；LOST 也纳入 |
| 已结束/活动槽位秒数 | 各尝试占用区间的和；活动区间尚未结束，以当前快照时间截断 |
| 过程结果 | 成功、失败、超时、取消、未创建进程即失败分别计数；超时的退出码 0 不算成功 |
| 重试 | 发生重试的不同任务数量，与额外尝试次数分别统计 |
| 历史质量记录 | 各类 gate 的记录次数，以及批准、拒绝、返工决定次数；已撤销历史仍属于发生过的事实 |

每种时长提供样本数、min/p50/p95/max/mean。分位数使用 nearest-rank；没有样本时返回 null，不制造“零秒成功”。时间来自控制器事件的墙上时钟；负间隔被排除并计数，时间逆序单独报告。全局容量始终包含所有项目，按项目筛选只改变统计样本范围。

一次预留可能对应多个前面释放事件的“下一次预留”。这个指标没有将某一物理槽位与任务建立因果绑定，也不证明当时一定存在可派发积压。不能把它直接称为纯调度延迟。

### 尚不能推导的指标

返回的 `unavailable` 明确列出证据缺口：持续 eligible 的排队时间、纯调度开销、完整交付周期、技术检查首次通过率、集成冲突率，以及完整的 CPU/内存/模型用量。原因包括未持久记录 eligibility 转换、没有固定交付任务集合、检查和冲突历史尚未全部结构化。

过程成功不等于质量通过，历史 gate 不等于当前仍有效的证明，占槽率不等于项目提速。精确质量门槛仍应读取当前证据；最终交付仍需要指定 reviewer。真实模型的串行/并行质量与效率对照尚未完成。

### 指标预算和完整性

一次快照最多覆盖 100,000 个事件、10,000 个任务、20,000 个尝试，需解析的事件明细总量最多 16 MiB。超出时返回 `METRICS_LIMIT`，不悄悄截取一段历史。登记、预留、启动、终态和释放记录与当前任务/尝试的结构不一致时返回 `METRICS_INCONSISTENT`。

`history.complete=true` 表示此次查询在预算内覆盖了选定范围的保留账本历史，并通过已实现的一致性检查；它不是外部审计、日志不可篡改证明或完整业务交付证明。

## 4. 继续寻找合理并行机会

协调器按以下顺序推进已批准工作：

1. 使用固定提交的源码读取接口，确认模块、契约、数据和可变资源是否可独立处理。
2. 用 `parallel_queue` 查看现有任务和准入原因，避免重复创建正在等待依赖或资源的任务。
3. 有独立且有价值的工作时，登记完整任务定义；容量已满时保留在队列中。
4. 让唯一控制器按真实完成事件释放和补位，不开启第二套原生 Agent/Workflow 队列。
5. 根据指标与实际质量证据调整后续拆分和已批准优先级，不为填满槽位扩大需求或降低检查要求。

`run --watch` 继续接收后来登记的任务，但不自动创造新需求，也不能唤醒已经退出的主 Agent 会话。任务没有合理的独立执行条件时，允许槽位空闲。

## 5. 同轮修复

- 初始 `recover_completed` 对账纳入取消处理；此时收到取消也会向已有真实进程请求停止。未知退出仍占槽，可靠退出仍只释放一次。
- Codex App Server 输入中的超大 JSON timeout 整数改为受控拒绝；验证失败不会启动原生进程。
- ZCode 使用 `--prompt=<文本>`，真实原生解析器已验证以 `--` 开头的提示词不会变成选项。独立事件解析器同时拒绝深层非有限数、重复键和无效 Unicode。
