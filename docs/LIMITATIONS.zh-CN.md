## 2. “并发上限”具体约束什么

上限约束的是账本管理的执行实例，包含实现 Worker、验证和集成任务，以及未确认退出的实例。它不会自动统计用户另行启动的 agent、其他控制器状态目录、任意 shell 中启动的独立 CLI、全部操作系统进程，或提供商侧的请求。

一个验证任务可以运行普通测试子进程，整个后代树由该任务的生命周期占用覆盖；这不是一个测试进程占用一个独立模型 Worker 槽位。CPU、内存、GPU、提供商 token 速率和费用上限需要额外的 OS/服务配置，当前数字并发上限不能替代这些预算。

任务完成事件触发释放和补位，单个慢任务不会把其他已空出的容量锁到整批结束。但源码复制、进程确认、SQLite 事务、事件循环和宿主启动都有实际耗时，因此没有毫秒级回填 SLA。

提供商通道另外限制本代理中的全局/单提供商在途请求，每个任务通道同时最多一条请求；请求预算在发出前持久扣减，失败不退款。它们与受管任务槽分开记账。撤销通道可以结束本地请求权限，却不能证明提供商侧计算或计费已经停止，也不构成 Worker 进程树退出证据。

## 3. 协作模式的信任边界

协作模式要求显式 `--acknowledge-cooperative`。所有参与进程作为同一 OS 用户运行；目录权限、隐藏身份文件、英文提示词和独立 Git 副本不能阻止恶意或不守规则的同用户进程。

控制器会在受控路径上执行原子准入、资源互斥、代次检查、进程身份检查、候选审计和审核身份检查。协作模式不会因此获得 OS 隔离。严格后端通过独立命名空间、按范围挂载和 seccomp 隐藏控制器、审核凭据、其他工作区及宿主服务。正式原生任务要求新鲜的部署验收；当前机器存在不支持迁移的管理策略，保持 blocked。

Worker 的自动环境继承采用精确允许列表，保留明确的 CLI/提供商配置，并拒绝控制器、其他连接器及权限代理的会话凭据。未列出的自定义引擎环境变量不会自动传入；需要在适配器中明确审核支持。该过滤不改变同用户配置文件可访问的边界。

当前不会为每个任务自动创建数据库、网络命名空间、独立端口池或所有语言的构建缓存。任务应声明外部独占资源并配置独立输出位置。资源名称必须由规划者统一，两个不同字符串不会被自动推断成同一个端口或数据库。

上述段落描述协作模式。严格离线模式为每个命令创建真正的网络命名空间，既不配置外网也不启用 loopback，并禁止非 UNIX socket。它不适合需要 TCP 服务、联网下载依赖或调用模型的检查；这些需求必须明确接入后续受限网络能力，不能通过共享宿主网络绕过。

显式的提供商模式只在自己的网络命名空间启用 IPv4 loopback，没有外部接口/路由；它经单次任务的 socketpair 访问控制器代理，不能把宿主网络作为退路。该模式不开放依赖下载、任意 HTTP 代理、远程工具或检查联网。宿主配置通过密封内存文件只读挂载，模型与质量值缺失或不匹配会拒绝；不自动选默认值以求通过。

### 严格离线后端的具体边界

- 以只读源码作为基底，只有任务声明的既有文件或目录可写；`.git` 始终只读。缺失的精确文件范围、链接别名、特殊文件或不受支持的运行时挂载会阻断。
- 每条验证命令有自己的只读源码沙箱。可信报告服务位于外部，测试无法写入控制器的报告、检查清单或退出 journal；私有 `/tmp` 中同名路径不代表宿主文件。
- 单文件挂载只支持原位写入，不能原子替换或删除挂载点；完整模块的正常新建、重命名和删除应使用已批准的目录范围。
- 工具链只读但可读。不要把私人数据放入明确授权的工具链/输入目录。未知工具链不会自动挂载整个父目录。
- 当前不提供 cgroup CPU、内存、进程数或临时文件总量硬配额；一个受管 Worker 可有普通编译/测试子进程。并发槽不是抗资源耗尽限制。
- x86_64 已实测；aarch64 有过滤表，仍需目标机器现场验证。管理员、内核漏洞及已在沙箱外运行的恶意同账户进程不属于此边界可保护的范围。

完整信任假设、系统调用和启动证明见 [英文隔离契约](STRICT-SANDBOX-CONTRACT.en.md)。

## 4. Hook、Skill 和原生 agent 能力

Skill 与 AGENTS 提供英文行为指导。Hook 对确实到达它的同步调用执行协议检查和拒绝；它不是拦截所有系统调用的防火墙。

已核对的 Codex 父会话标识不一定唯一对应子 Worker；SubagentStop 不证明线程关闭或进程树退出。ZCode 普通 Agent 子代理在已审阅路径上不继承父 Hook runner；异步 Agent 的启动返回也不代表结束。ZCode `onError: deny` 不覆盖所有跳过、无效输出和解析路径。

因此，回收容量和最终审核不依赖这些 Hook 消息。受管 Codex CLI 禁用原生多代理工具；受管 ZCode CLI 关闭原生工作流并禁用派发/恢复工具。任意 shell 再启动一套 agent 仍需要独立 OS/网关边界才能强制阻止。

当前 CLI 没有为 Stop 实现持久续行预留，故默认不阻止 Stop 以强行继续聊天。纯处理器支持“控制器已预留且最多两次”的条件；实际持续队列由 `run --watch` 实现。Hook 和 watch 进程都不会自动唤醒已经结束的协调器会话。

### 首个原生独立 API 配置的范围

Codex 通过 App Server 在已经证明的外部 Linux 沙箱内运行。该模式无法证明与所有原生审批规则等价，因此存在 `/etc/codex` 管理策略、项目或祖先 `.codex`、`.agents` 技能/插件目录、独立 Hook 配置时拒绝；不要移除既有策略绕过判断。支持的 AGENTS 指令按路径和字节固定，源项目、实际工作副本、启动及完成时都检查。可写范围不能覆盖现有指令文件。

项目本地插件安装通常引入 `.agents` 或 `.codex`，所以不能把安装流程与这个有限的独立 Worker 配置直接等同。协调器插件可以运行在另一个受信任工作环境，受管项目必须自身满足部署要求。动态链接 Codex、脚本入口、ZCode 运行依赖闭包和完整原生策略迁移尚未支持。详见 [原生执行契约](NATIVE-HOST-CONTRACT.en.md)。

## 5. 自动寻找并行机会的范围

代码会根据已批准任务图、依赖门槛、验证积压、资源适配和完成事件寻找可执行工作，并自动发现实现后的验证、当前候选的集成等阶段任务。它不会自行调用一个额外模型来不断拆分产品需求，也不会仅为了填满槽位扩大任务范围。

协调器可通过有界 MCP 读取固定提交源码，并在已批准计划内登记任务；它不能读取任意宿主路径或未提交文件。业务模块是否语义独立仍由协调 agent、Skill 指导和人工/外部审核判断。不同文件不保证无逻辑冲突：公共 API、行为假设、数据迁移、依赖锁文件、部署顺序和共享运行资源都可能耦合。程序可以检查声明的一致性，不能证明未被声明的依赖不存在。

当前队列通过优先级和年龄选择工作，验证任务优先级较高；没有声称实现了完整的最优关键路径求解、CPU/内存自适应装箱或学习型成本预测。

## 6. 依赖、返工与版本管理

运行流水线使用 `contract_ready` 和 `implementation_verified` 进行同一计划内调度：前者由可信规划入口记录冻结接口；后者需要实际候选通过检查，下游使用已验证对象建立源码基线。

下游声明 `integrated_verified` 或 `final_accepted` 时，流水线可先组合已经验证的上游集合，供阶段门槛使用。最终接受仍等待指定独立审核；默认没有可执行任务时 `run` 会退出，审核后需重启；`run --watch` 可以等待审核或新任务，直到会话截止时间。账本保留符合当前计划及失效代次约束的不可变集成交付/审核历史，使已派发的下游能绑定当时实际使用的交付，而非被后来的集成摘要静默替换。新候选、新计划、取消或明确撤销仍会使相关旧证明失效；历史记录不能用于绕过变更。新组合的交付摘要需要自己的最终批准。

任务 ID 是不可变定义。计划 revision 更新需要旧实例结束，并使旧任务、候选和门槛失效。拒绝/返工不会自动重开旧任务。当前计划中保留一个被阻断的原始任务，不会因为登记一个“替代名称”的任务就变成整项计划完成。阶段集成只证明其明确候选集合，需要明确的计划修订和新任务图处理返工。

## 7. 检查报告的适用范围

检查运行在精确 Git 候选上，要求起始文件与提交一致，包括未跟踪文件检查；检查后源码必须保持不变。检查可用普通命令执行，必需但未提供 argv 的条件会成为 `not_run`，而非通过。没有实际执行的人类视觉验收、性能实验或生产回归必须保留未完成状态。

默认临时目录/缓存放在验证副本之外。程序只会清理自己新建并确认后代进程已退出的 `.parallel-dev-check-tmp`；已有同名目录不会接管。其他生成文件会使范围/完整性检查失败，应明确设置工具输出目录。

环境摘要包含平台、运行器、可执行文件和规定设置，不记录环境变量秘密值。它没有锁定全部系统库、网络服务、测试数据或外部依赖，不能据此声称 hermetic build。日志有界并标注截断；完整日志需求应通过批准的外部日志方式提供，不应把截断结果称为完整输出。

源码快照限制为 100000 个文件、总量 2 GiB；每份检查 manifest 最多 128 个检查，合并候选后的组合检查也受这一边界约束。当前检查器要求私有 Git checkout，不支持子模块或非 UTF-8 Git 路径。大仓库、复杂构建和特殊文件系统应先检查这些边界。

## 8. 恢复、重试与保留数据

控制器重启会对账持久 outbox、启动身份、退出证明和后处理记录。数据库事务不能与 OS 创建进程原子提交，所以“启动过但确认丢失”必须保留不确定状态。心跳过期、supervisor PID 消失或缺少日志都不足以证明整个后代树结束。

LOST 实例继续占用安全容量，不自动派出替代实例。当前没有一条强制清零不确定实例的命令；需取得真实终止证据或实现有效的资源撤销边界后恢复。不要为了看到空槽位而编辑数据库、复用旧代次或删除 journal。

账本具有最多两次重试、退避和幂等语义；当前业务流水线会阻断无法分类的宿主失败和检查失败，避免重复外部副作用。它没有对每一种宿主错误建立可自动重试的安全分类。

发布意图和引用 CAS 的恢复已实现，但某些无法证明结果的情况会继续保留发布租约并阻断后续计划修改。这是要求诊断的状态，不是可随意删除的死锁标记。

工作副本、候选、日志、审核和发布证据会保留以支持恢复；本版本没有完整的自动保留期限或垃圾回收管理 CLI。删除前要确认没有活动/不确定实例及未结束发布，并保留所需审核证据。

## 9. 安装、发布和宿主支持

发行物是 Python 源码包，要求宿主能找到 Python 3.11+。Windows 的 `py -3` 加载声明不代表已经构建或验证了原生 `.exe`。Codex 采用 portable manifest/MCP 和兼容 manifest；ZCode 按固定来源的插件目录及 Hook/MCP 解析规则生成。上游版本变化可能影响参数和信任流程，doctor 的 help 探测不能替代实际联调。

插件不会静默修改全局配置、申请仓库 OAuth、登录宿主、授予 Hook 信任或发布远程版本。源码或压缩包可供本地评审使用；是否已经推送到远端、安装到宿主或通过正式发行审核，应以相应实际记录为准。
