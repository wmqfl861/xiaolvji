## 1. 本轮解决的问题

| 问题 | 实现后的行为 | 验证依据 |
| --- | --- | --- |
| 旧任务可能被不断到来的高优先级/验证任务插队 | 优先级加角色加分，按登记年龄共同老化到 120；同分时先登记者优先 | 固定时钟、重启、持续 verifier 到达等账本测试 |
| READY 没有解释实际为何无法派发 | `queue` 返回依赖、退避、全局/项目容量、写范围、资源和重试预算阻塞；与 reserve 共用规则 | 真 SQLite 并发、资源租约、文件范围和快照测试 |
| 只有原始事件，缺少可审查的统计口径 | `metrics` 从一致快照汇总等待、槽位秒数、释放间隔、重试、过程结果和历史质量记录 | 已知时间序列、真实审核 API、并发写入、时钟倒退和缺失历史测试 |
| 诊断输出受限，背后却可能读取过大总体 | 查询先执行固定总体/明细预算；超限明确拒绝，截断状态明确 | 小预算负面测试和生成包接口测试 |
| 初始恢复等待期间取消不进入清理逻辑 | 初始 reconcile 纳入取消处理；真实已有进程收到取消，未知实例仍占槽 | 真实 SQLite 与事件控制的模拟 gateway，覆盖确认退出/未知分支及重复退出 |
| 超大 JSON timeout 整数导致未捕获数值溢出 | 先核对类型和范围，返回有界结构化失败，零原生进程启动 | 输入/标准输入入口回归 |
| ZCode 将以 `--` 开头的提示词当成参数 | 使用单个 `--prompt=<原始文本>`，保留完整内容 | 固定源码中的真实参数解析器运行七类生产 argv，含两种 120,000 字节边界 |
| 事件 JSON 深层指数溢出可变成无穷大 | 共享严格解析器拒绝非有限数、重复键、无效 Unicode 和过深嵌套 | 有界失败及错误文本脱敏回归 |

Queue 的 `dispatchable` 是逐任务观察，不代表所有返回项能一起启动；它不预留容量。统计中的登记年龄不等于连续 READY 时长，释放间隔不等于纯调度开销，历史 gate 不代表当前有效证明。完整口径见[调度与指标](SCHEDULING.zh-CN.md)。

## 3. 最大合理并行的实际机制

同一资源域只有一个 Dispatcher 和一个账本。不同任务能否并行，先看已批准的依赖门槛、文件所有权和独占资源，再看全局与项目容量。两个路径不同的任务仍可能在接口、迁移、锁文件或测试资源上冲突，语义独立性仍由协调器分析并声明。

有容量就逐项原子预留和派发；满槽时停止新增；收到可靠的完整进程树退出证明后释放并唤醒调度，不等同批最慢任务。`run --watch` 跨空闲期等待后来登记的批准任务；本进程完成事件唤醒队列，外部登记通过短轮询发现。该机制不承诺硬实时，也不会自行创造额外需求。

排序中的质量加分是有限偏好，必须的实现、集成和审核门槛始终存在。最低优先级任务达到共同分数上限需要 3,600 秒登记年龄，但容量、依赖或冲突阻塞仍可能继续等待。这不是“一小时内启动”的保证。

未知实例继续占槽。取消、模型完成消息、Hook、HTTP 断线或主 PID 消失都不能代替退出证据。会话截止只取消再次检查时仍活动的实例，保留未准入任务、完成证据和项目启用状态；明确的项目取消继续保留更广的禁用与撤销语义。初始恢复现在也在取消覆盖范围内。

## 4. Codex 与 ZCode 的真实证据

### Codex

实际二进制是 `codex-cli 0.167.0-alpha.4`。原生合成协议验收使用真实 App Server、真实工具调用、实际隔离和私有模型通道。六项原生测试包括 13 项固定边界断言、精确质量字段、多轮工具调用、取消、管理策略拒绝和未知模型拒绝。它们不调用真实外部模型，也不证明实际模型的代码质量。

正式路径要求 `host verify` 对目标部署、二进制、运行时代码、系统工具、启动身份、项目指令和精确配置建立一致记录。每次运行重新检查。当前机器存在 `/etc/codex` 管理策略，首个独立 API 配置不能完整迁移它，因此继续在凭据读取和模型请求之前阻断。没有删除策略、降低 profile 或换模型来绕过。

### ZCode

固定源码为 `a60ba6a7e5a06742270ca605f5d2cc2766afa7e1`。完整源码的 59 个 package manifest 及 workspace 包可核对；此前“公开仓库缺少 provider/schema”的判断已修正为本地稀疏副本问题。

本版将 Git blob 绑定范围扩展到 11 个真实源码文件：原有七种模型选项映射、负面对照、Agent 别名和代理环境清理仍执行；新增七类生产 argv 通过原生 extractor 与 global parser，另有三个负面对照复现旧 split-argument 缺陷。没有用 stub 替换该解析器。

一次公开依赖获取检查仍返回 `EAI_AGAIN`。完整 CLI 外置了 `@zcode/tui`、`playwright-core`、`koffi`，所以仅复制入口脚本并记录摘要不足以证明依赖闭包可运行。完整 CLI、配置 schema 和真实模型未执行，所有对应 readiness 标记继续为 false。详情见[ZCode 兼容性](ZCODE-COMPATIBILITY.en.md)。

## 5. 指标覆盖与后续开发顺序

本版统计真实账本事实，同时明确缺少持续 eligible 转换、固定交付集合、全部结构化检查尝试、集成冲突分类和完整资源/模型用量，不能直接给出这些项目的率值或效率结论。

后续应依次推进：

1. 在符合独立部署契约的目标机器完成 Codex 真实提供商与安装后的插件联调，或先实现并验收现有管理策略完整保留。
2. 在能取得固定工具链和依赖的环境构建 ZCode，绑定解释器、外置模块、原生资产和真实运行闭包，再验收权限、取消和恢复。
3. 持久化精确 eligibility 转换、结构化检查/冲突与交付集合，补全所需指标，再用同一任务、质量标准和模型做串并行对照。
4. 分别验证其他平台、资源硬配额、长期故障恢复和独立正式发布审核。

这些工作不会被本地全绿测试自动视为完成。交付保留可继续开发的源码和证据，正式批准仍属于指定 reviewer。
